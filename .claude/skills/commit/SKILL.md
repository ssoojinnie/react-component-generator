# commit: 변경사항 분석 후 컨벤션 커밋

현재 작업 디렉토리의 변경사항을 읽고, 의미 단위로 묶어, 저장소 컨벤션에 맞는 한국어 커밋 메시지를 제안한다. **사용자가 명시적으로 승인한 뒤에만 커밋한다.**

인자가 주어지면 그 범위로 한정한다(예: `/commit 로그인 버그만` → 해당 변경만 커밋하고 나머지는 그대로 둔다).

## 워크플로우

### Step 0: 사전 확인

1. **git 저장소인지 확인한다.** `git rev-parse --git-dir`이 실패하면 커밋할 수 없다. 사용자에게 알리고 `git init` + 첫 커밋을 할지 물어본 뒤, 승인하면 진행하고 아니면 종료한다.
2. **저장소 지침을 읽는다.** 루트의 `AGENTS.md`(없으면 `CLAUDE.md`)에 커밋 메시지 규칙·커밋 전 검증(린트/테스트) 요구가 있으면 그것이 이 스킬의 기본값보다 우선한다. 모노레포에서 하위 디렉토리에 중첩 지침이 있으면 해당 파일에 가장 가까운 지침을 따른다.
3. **기존 커밋 컨벤션을 확인한다.** `git log --oneline -20`으로 실제 쓰이는 형식을 본다. 저장소가 이미 다른 규칙(영어 메시지, 이슈 번호 접두사, `[scope]` 표기, gitmoji 등)을 쓰고 있으면 **아래 기본 형식이 아니라 저장소 관행을 따른다.** 커밋이 없는 새 저장소면 기본 형식을 쓴다.
4. **브랜치를 확인한다.** `main`/`master` 등 기본 브랜치에 있으면 커밋 전에 작업 브랜치를 만들지 사용자에게 물어본다. 사용자가 현재 브랜치에 그대로 커밋하겠다고 하면 그대로 진행한다.

### Step 1: 변경사항 분석

다음을 모두 확인한다. 하나라도 빠지면 커밋 단위를 잘못 나눈다.

```
git status --short          # 추적/미추적/스테이징 상태 전체
git diff                    # 스테이징되지 않은 변경
git diff --staged           # 이미 스테이징된 변경
```

- **미추적 파일(`??`)을 놓치지 않는다.** `git diff`에는 보이지 않으므로 `git status`로 확인하고, 필요하면 내용을 직접 읽는다.
- diff가 커서 잘릴 때는 파일 단위로 나눠 읽는다(`git diff -- <path>`). 요약만 보고 추측하지 않는다.
- 이미 스테이징된 변경이 있으면 **사용자가 의도적으로 올려둔 것일 수 있다.** 그 범위를 그대로 첫 커밋으로 쓸지, 아니면 전체를 다시 나눌지 Step 3 제안에 명시한다.
- 각 변경이 **무엇을 왜 바꿨는지** 파악한다. 파일명만으로 추측하지 말고 diff 내용을 근거로 삼는다.

#### 커밋에서 제외할 것

다음은 스테이징하지 않고, 발견하면 사용자에게 알린다:

- **비밀정보**: `.env`, `*.pem`, `id_rsa`, API 키·토큰·비밀번호가 하드코딩된 변경. 이미 추적 중인 파일에 키가 새로 들어갔으면 커밋을 멈추고 먼저 알린다.
- **빌드 산출물·의존성**: `dist/`, `build/`, `node_modules/`, 로그 파일. `.gitignore`에 빠져 있으면 `.gitignore` 추가를 별도 단위로 제안한다.
- **디버깅 잔여물**: 임시 `console.log`, 주석 처리한 코드 덩어리, 스크래치 파일. 의도한 변경인지 사용자에게 확인한다.

### Step 2: 논리적 단위로 분류

**한 커밋 = 하나의 의도.** 되돌릴 때 함께 되돌아가야 하는 변경만 같은 커밋에 넣는다.

분류 기준:

- **의도로 묶는다.** 같은 기능을 위한 변경은 파일이 달라도 한 커밋(예: 컴포넌트 + 스타일 + 테스트). 반대로 한 파일 안에 버그 수정과 리팩터링이 섞여 있으면 두 커밋으로 나눈다(`git add -p` 사용).
- **독립적으로 설명되면 나눈다.** 메시지에 "그리고"를 써야 한다면 두 커밋이다.
- **의존 순서를 지킨다.** 각 커밋이 그 자체로 빌드되는 순서로 배치한다. 리팩터링·설정 변경을 기능 변경보다 앞에 둔다.
- **단위가 5개를 넘으면** 묶을 수 있는지 다시 검토하고, 그래도 많으면 그대로 제안하되 왜 나눴는지 한 줄로 설명한다.

### Step 3: 한국어 커밋 메시지 작성

#### 형식

```
<type>: <요약>

<본문 (선택)>

Co-Authored-By: <현재 세션의 모델 트레일러>
```

- **type**: `feat`(기능 추가) / `fix`(버그 수정) / `refactor`(동작 변화 없는 구조 개선) / `chore`(빌드·설정·의존성·문서 등 그 외). 저장소 로그에 `docs`·`test`·`style` 같은 타입이 이미 쓰이고 있으면 그것도 쓴다.
- **요약**: 한국어 50자 이내, 마침표 없이. **무엇을 했는지 평서형으로 끝낸다**(`추가`, `수정`, `분리`, `제거`). "~했음", "~하기" 같은 어미나 "업데이트", "변경" 같은 뭉뚱그린 단어는 쓰지 않는다.
- **본문**: 요약으로 부족할 때만 쓴다. **무엇을 바꿨는지가 아니라 왜 바꿨는지**를 적는다(diff를 보면 무엇인지는 알 수 있다). 여러 항목이면 `-` 불릿.
- **트레일러**: harness가 지정한 `Co-Authored-By:` 트레일러를 마지막 줄에 붙인다. 모델명은 현재 세션 기준으로 쓴다.

#### 예시

```
feat: 프롬프트 예시 클릭으로 입력창 채우기 추가

fix: API 키 없이 생성 시 요청이 전송되던 문제 수정

refactor: 생성 로직을 useComponentGenerator 훅으로 분리

커밋 메시지 본문 예:
chore: eslint에 react-hooks 규칙 추가

훅 의존성 누락으로 미리보기가 갱신되지 않는 버그가 반복돼
CI에서 먼저 잡도록 규칙을 켠다.
```

### Step 4: 승인 요청

커밋하기 **전에** 계획 전체를 한 번에 보여준다. 단위별로 다음을 표시한다:

```
1. feat: 프롬프트 예시 클릭으로 입력창 채우기 추가
   src/components/PromptInput.tsx
   src/components/PromptInput.test.tsx

2. chore: 레트로 테마 작업 중단으로 되돌린 스타일 정리
   src/App.css
```

- 제외한 파일이 있으면 **이유와 함께** 함께 보여준다(`.env` — 비밀정보, 스테이징 안 함).
- 선택지가 단순 승인/거절이 아니면(예: 단위를 묶을지 나눌지) `AskUserQuestion`으로 묻는다.
- **사용자가 승인하기 전에는 `git add`도 `git commit`도 실행하지 않는다.** 분석 단계의 읽기 전용 명령만 쓴다.
- 사용자가 메시지나 분류를 수정하면 반영한 계획을 다시 보여주고 재승인을 받는다.

### Step 5: 커밋 실행

승인된 단위를 순서대로 커밋한다.

- **파일을 명시해 스테이징한다**: `git add <path> <path>`. `git add -A`·`git add .`는 의도하지 않은 파일을 끌어들이므로 쓰지 않는다. 한 파일에서 일부만 커밋해야 하면 `git add -p`를 쓴다.
- 커밋 직전 `git status --short`로 스테이징 내용이 계획과 같은지 확인한다.
- 멀티라인 메시지는 heredoc으로 전달한다:

```
git commit -F - <<'EOF'
feat: 프롬프트 예시 클릭으로 입력창 채우기 추가

Co-Authored-By: ...
EOF
```

- **훅이 커밋을 막으면 `--no-verify`로 우회하지 않는다.** 훅 출력을 읽고 원인을 고친 뒤 다시 스테이징해서 커밋한다. 훅이 파일을 자동 수정했으면 그 변경을 다시 스테이징해야 한다.
- 커밋이 실패하면 **남은 단위를 계속 커밋하지 말고 멈춘다.** 어디까지 커밋됐는지와 실패 원인을 보고한다.
- 저장소 지침이 커밋 전 린트·테스트를 요구하면 그때만 실행한다. 지침에 없으면 기본적으로 실행하지 않는다(필요해 보이면 승인 단계에서 제안한다).

### Step 6: 결과 보고

`git log --oneline -<커밋 수>`로 확인하고 생성된 커밋을 보고한다. 커밋되지 않고 남은 변경이 있으면 무엇이 왜 남았는지 함께 알린다.

## 하지 않는 것

- **push 하지 않는다.** 사용자가 별도로 요청할 때만 한다.
- **기존 커밋을 고치지 않는다.** `commit --amend`, `rebase`, `reset`, 강제 push는 이 스킬의 범위가 아니다. 사용자가 명시적으로 요청하면 되돌릴 수 없는 작업임을 알리고 확인을 받은 뒤에만 한다.
- **버려진 작업을 커밋하지 않는다.** 사용자가 취소·중단한 작업의 잔여 변경이 보이면 커밋 대상에 넣기 전에 확인한다.
- **변경을 만들지 않는다.** 이 스킬은 기존 변경을 커밋할 뿐이다. 커밋하다가 발견한 버그는 보고하고, 고치려면 별도 승인을 받는다.
